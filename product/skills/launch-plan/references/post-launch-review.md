# Post-launch review template

Set the date before launch. Hold it even if things went well. Focus on decisions and systems, not on blaming people.

```markdown
# Post-launch review: <launch name>

Review date: <Day +N> · Data cut-off: <Day +M> · Decider: <role>

## Decision

<Pass / iterate / stop (or the rule the plan set), in one line, with the number that decided it.>

## Against the plan

| Metric or gate | Threshold set before launch | Result | Met? |
|---|---|---|---|

## Watch list and incidents

| Signal | Alerts fired | What we did | Time to act |
|---|---|---|---|

## Rollback

<Was any trigger hit? Did the mechanism work as rehearsed? If nothing was hit, say so.>

## What users told us

<Themes from support, interviews and feedback, each with how many people raised it. No names.>

## What surprised us

<Things the plan didn't predict. These become readiness items next time.>

## Commitments carried

<Deletion requests honoured on time? Data handled as consent said? Flags removed?>

## Next

<If pass: the next stage and the date its plan is due. If iterate: the one thing to change and the re-run. If stop: what to learn and from whom.>
```

## Rules

- Apply the decision rule as written before launch. If you want to change it now, say so openly and record why.
- Count people, not percentages, for small cohorts.
- Report a missing number as missing, with why. Don't estimate it into the table.
